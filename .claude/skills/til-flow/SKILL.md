# til-flow

eodigakka 프로젝트의 시행착오 기록 + 4문서 일괄 갱신 워크플로우.

`CLAUDE.md`에 명시된 규약(TIL 의무화 섹션)을 자동화한다.

---

## 트리거 판단

### 적용해야 할 때

다음 신호 중 하나라도 있으면 트리거를 우선 제안한다:

- 버그 수정 끝났다는 메시지/코드 변경
- 30분 이상 디버깅 끝에 원인 발견
- 에러 메시지가 직관적이지 않은 케이스 (인자 순서, 코드 체계 불일치, ABI 충돌 등)
- 외부 API/라이브러리의 의외 동작 발견 (예: `translate=True`가 NaN을 문자열로 변환)
- 환경 설정 문제 해결 (Python 버전, MCP 등록, 컨테이너 마운트 등)
- 같은 함정에 다시 빠질 가능성이 있는 모든 케이스

### 적용하지 않아야 할 때

- 단순 오타·import 누락 같은 자명한 실수
- 1회성 데이터 정리 명령 (`rm`, `mv` 등)
- 이미 README/SPEC에 명시된 정보의 중복
- 사용자가 명시적으로 "기록 안 해도 돼"라고 한 경우

## 입력 추출

대화 컨텍스트에서 4가지를 뽑는다. 부족하면 사용자에게 한 번 묻는다 — 한 번에 묶어서.

| 슬롯 | 무엇 | 어디서 추출 |
|---|---|---|
| **현상** | 무엇이 안 됐나 | 에러 메시지, 디버그 출력, 재현 명령어 |
| **원인** | 왜 그랬나 | 디버깅 과정에서 확인한 사실, 비교 표 |
| **수정** | 어떻게 고쳤나 | 코드 diff, 명령어 변경 |
| **교훈** | 일반화된 규칙 | 다음번 어디서 다시 만날지 추론 |

추가로 판단:
- **아키텍처 결정 포함 여부**: 코드 체계 변경, 의존성 교체, 도메인 모델 마이그레이션 같은 결정이면 SPEC ADR도 추가. 단순 버그 수정이면 ADR 불필요.
- **태스크 영향**: `tasks.md`에서 `[~]` → `[x]`로 옮길 항목, 새로 추가할 블로커가 있는지.

## 산출물

다음 4(+1)개 파일을 같은 단위(같은 커밋 묶음)로 갱신한다.

### 1. `docs/til/YYYY-MM-DD-짧은-키워드.md` (신규)

파일명 규칙: 날짜 + 핵심 단어 1~3개 (영문 kebab-case 또는 짧은 한글-영문 혼용).

본문 4단락 고정 양식:

```markdown
# TIL: <한 줄 제목>

날짜: YYYY-MM-DD

## 현상
<무엇이 안 됐나 — 에러 메시지·재현 명령어 포함. 표·코드블록 활용>

## 원인
<왜 그랬나 — 가능하면 비교 표(예: `translate=True` 전후, 행정동 vs 법정동)로 보여라. 추측하지 말고 확인된 사실만 적는다.>

## 수정
<어떻게 고쳤나 — 변경 전/후 diff 또는 명령어. 결정의 근거가 있으면 한 줄로.>

## 교훈
<다음번에 어디서 다시 만날지, 일반화된 규칙. 단순한 "조심하자"가 아니라 구체적 룰.>
```

표·코드블록·비교는 본문 풍부함의 일부. 4단락 헤더는 고정.

### 2. `CHANGELOG.md` (추가)

상단(가장 최근 날짜)에 항목을 추가한다. 같은 날짜 섹션이 이미 있으면 합치거나 별도 항목으로 추가.

```markdown
## [YYYY-MM-DD] <한 줄 요약>

### 결정 (ADR)        ← ADR-N이 추가된 경우에만
- ADR-N: <한 줄 설명>

### 수정
- `path/to/file.py` `func_name` — <무엇을 어떻게>
  - 원인: <한 줄>
  - 수정: <한 줄>

### 추가
- `docs/til/YYYY-MM-DD-키워드.md` — <원인·교훈 요약>
- (테스트 추가했다면) `path/to/test.py` — 회귀 테스트
```

### 3. `tasks.md` (갱신)

- 완료된 항목 `[ ]` → `[x]` 또는 `[~]` → `[x]`
- 발견된 새 블로커는 `[ ]`로 추가, 가능하면 세부 단계까지 분해
- TIL 참조는 `(TIL <키워드>)` 한 줄로

### 4. `docs/til/README.md` (인덱스 갱신)

해당 날짜 섹션의 카테고리 아래 한 줄 추가:

```markdown
- [짧은 제목](YYYY-MM-DD-키워드.md)
```

날짜 섹션이 없으면 생성. 카테고리(MCP/API/ETL/DB 등)는 기존 분류를 따른다.

### 5. `SPEC.md` (조건부 — ADR 신설 시만)

`## 15. ADR (Architecture Decision Records)` 섹션에 ADR-N 추가 (N은 마지막 번호 + 1):

```markdown
### ADR-N: <한 줄 결정 요약> (YYYY-MM-DD)
- **결정**: <무엇을 결정했나 — 명확한 동사로>
- **근거**: <왜 — 데이터·제약·도메인 표준 인용>
- **영향**: <어떤 코드/뷰/테이블이 바뀌어야 하나>
```

## 실행 순서

1. **컨텍스트 스캔** — 직전 N턴의 대화에서 4슬롯(현상/원인/수정/교훈) 추출. 부족하면 묻는다.
2. **ADR 필요 여부 판단** — 결정 포함이면 yes.
3. **TIL 신규 파일 작성** — 4단락 양식 준수.
4. **CHANGELOG / tasks / README 인덱스 갱신** — 한 메시지에서 병렬 Edit.
5. **(조건부) SPEC.md ADR 추가**.
6. **자기 점검 — 4(+1) 파일 모두 갱신됐는지 확인**:
   - `docs/til/<file>.md` 신규 ✓
   - `CHANGELOG.md` 새 항목 ✓
   - `tasks.md` 상태 변화 ✓
   - `docs/til/README.md` 인덱스 한 줄 ✓
   - (ADR이면) `SPEC.md` §15 ADR-N ✓
7. **사용자에게 짧은 요약** — 어떤 파일이 어떻게 갱신됐는지 표 1개로.

## 양식 일관성 가드

- 모든 본문은 한국어. 코드 식별자·파일 경로는 원문.
- 단정문 금지 (`CLAUDE.md`의 9원리 준수). "원인" 섹션에서 추측은 "가능성" 명시.
- TIL "교훈" 섹션은 일반화된 규칙. "다음에 조심하자" 같은 문구 금지 — 구체적 룰만.
- `CHANGELOG.md` 항목 동사: 추가/변경/수정/결정/확인.
